# Контекст проекта CollectIT для написания текста ВКР

Этот файл предназначен для передачи нейросети, которая будет помогать писать текст выпускной квалификационной работы. В нем собрана информация о том, что реализовано в проекте, зачем это разрабатывалось, как устроена архитектура, какие интеграции подключены, какие пользовательские сценарии поддерживаются и какие технические решения можно описывать в ВКР.

В документе намеренно не указаны реальные ключи, токены, пароли и персональные данные. Для описания интеграций используются только названия сервисов и переменных окружения.

## 1. Краткое описание проекта

CollectIT - веб-платформа для коллекционеров, которая позволяет вести цифровые коллекции, публиковать предметы, искать интересующие лоты, общаться с другими пользователями, проводить сделки с удержанием средств, получать уведомления, читать новости и обращаться в поддержку.

Проект ориентирован на частных коллекционеров монет, марок, значков, винила, фарфора, открыток, антикварных предметов и других коллекционных объектов. Основная идея - объединить в одном сервисе личный каталог коллекции, витрину предметов, безопасную сделку, доставку, переписку и административный контроль.

Главная прикладная проблема, которую решает система: снизить риски при покупке коллекционных предметов между частными пользователями. Для этого реализованы:

- аккаунты с подтверждением email;
- профили и публичные страницы коллекционеров;
- коллекции и предметы с фотографиями;
- чат покупателя и продавца;
- сделка с удержанием средств;
- сервисный сбор платформы;
- интеграция с доставкой СДЭК;
- административные инструменты для споров;
- уведомления и поддержка;
- журнал транзакций и ручные заявки на вывод средств.

## 2. Цель разработки

Цель проекта - разработать полнофункциональную веб-платформу для коллекционеров, которая поддерживает не только хранение и демонстрацию коллекций, но и безопасное взаимодействие между пользователями при продаже предметов.

В рамках ВКР проект можно описывать как информационную систему с элементами маркетплейса, личного кабинета, CRM для обращений и административного контроля сделок.

Основные задачи разработки:

- реализовать регистрацию, авторизацию и профиль пользователя;
- дать пользователю возможность создавать коллекции и предметы;
- добавить галерею фотографий предметов;
- реализовать поиск и фильтрацию предметов;
- построить чат для общения покупателей и продавцов;
- разработать жизненный цикл сделки;
- добавить удержание средств до подтверждения получения товара;
- подключить платежный сценарий через ЮKassa;
- подключить выбор пункта выдачи СДЭК;
- реализовать ручной вывод средств на СБП или карту;
- добавить поддержку, уведомления и Telegram-сигналы администратору;
- автоматизировать публикацию новостей через Google Gemini;
- подготовить Docker-инфраструктуру и production-деплой на VPS;
- усилить безопасность API и пользовательских данных.

## 3. Пользовательские роли

В системе есть несколько уровней пользователей.

**Гость**

- видит информационную главную страницу;
- может открыть регистрацию или вход;
- может просматривать публичные разделы, если они доступны без авторизации.

**Зарегистрированный пользователь**

- создает профиль;
- заполняет телефон и пункт выдачи СДЭК;
- создает коллекции;
- добавляет предметы;
- добавляет фотографии предметов;
- выставляет предметы на продажу;
- ищет предметы других пользователей;
- добавляет предметы в вишлист;
- пишет сообщения другим пользователям;
- участвует в сделках;
- пополняет баланс;
- создает заявки на вывод средств;
- обращается в поддержку.

**Продавец**

- указывает цену предмета;
- видит свою цену без сервисного сбора;
- получает предложение в чате;
- нажимает согласие на продажу;
- после оплаты покупателем передает товар в СДЭК;
- после подтверждения получения покупателем получает деньги на баланс;
- может просматривать архив завершенных сделок.

**Покупатель**

- видит цену с сервисным сбором 7%;
- пишет продавцу;
- оплачивает сделку с баланса;
- ожидает доставку;
- подтверждает получение;
- ставит оценку продавцу;
- может просматривать архив завершенных сделок.

**Редактор новостей**

- имеет флаг `is_news_editor`;
- может создавать, редактировать и удалять новости;
- работает с изображениями новостей.

**Администратор**

- работает через Django Admin;
- видит пользователей, коллекции, предметы, сделки, транзакции, заявки на вывод, тикеты поддержки;
- может вручную вернуть удержанные средства покупателю;
- может вручную зачислить удержанные средства продавцу;
- обрабатывает заявки на вывод средств;
- получает Telegram-уведомления о тикетах поддержки.

## 5. Архитектура проекта

Проект разделен на backend и frontend.

Backend находится в папке `backend/` и состоит из Django-приложений:

- `accounts` - пользователи, регистрация, авторизация, баланс, транзакции, вывод средств, СДЭК, ЮKassa;
- `collectibles` - коллекции, предметы, галерея фотографий, вишлист;
- `chats` - чаты, сообщения, сделки, WebSocket, эскроу;
- `news` - новости, изображения новостей, AI-импорт с Numizmatik.ru;
- `notifications` - уведомления внутри платформы, email и Telegram;
- `support` - тикеты поддержки и сообщения по тикетам;
- `search` - поиск предметов;
- `collectit` - настройки проекта, ASGI, Celery, общие security-утилиты.

Frontend находится в папке `frontend/` и представляет собой React SPA. Основные страницы:

- `HomePage` - информационная главная страница;
- `LoginPage` и `RegisterPage` - вход и регистрация;
- `VerifyEmailPage` - подтверждение email;
- `ProfilePage` - профиль, коллекции, предметы, архив сделок;
- `SettingsPage` - настройки профиля, телефон, ПВЗ СДЭК;
- `SearchPage` - поиск предметов и фильтры;
- `NewsPage` - лента новостей;
- `BalancePage` - баланс, транзакции, заявки на вывод;
- `SupportPage` - обращения в поддержку;
- `AdminTicketsPage` - интерфейс администратора для тикетов;
- `OnboardingPage` - игровое обучение новичка.

Frontend обращается к backend через `/api`. В Docker и production запросы идут на тот же origin, что важно для httpOnly cookie. WebSocket-подключения идут через `/ws/chats/{id}/` и `/ws/notifications/`.

## 6. Модель данных

### 6.1. Пользователь

Модель пользователя расширяет стандартного пользователя Django. Добавлены:

- уникальный email;
- avatar;
- bio;
- дата регистрации;
- статистика: количество предметов, коллекций, сделок;
- рейтинг;
- баланс;
- количество просмотров профиля;
- роль редактора новостей;
- телефон;
- город и пункт выдачи СДЭК;
- необратимый прогресс онбординга.

Вход выполняется по email. Username остается как публичное имя пользователя.

### 6.2. Подтверждение email

При регистрации создается не пользователь сразу, а `PendingRegistration`. В ней хранятся:

- username;
- email;
- хэш пароля;
- токен подтверждения;
- дата создания;
- срок истечения.

Пользователь создается только после перехода по ссылке подтверждения из письма. Это уменьшает количество мусорных аккаунтов и подтверждает владение email.

### 6.3. Баланс и транзакции

Для учета денег есть модель `Transaction`. Она фиксирует:

- пользователя;
- тип операции: пополнение или списание;
- сумму;
- описание;
- ID платежа ЮKassa;
- дату создания.

Для защиты от двойного зачисления платежа добавлено ограничение уникальности по `payment_yookassa_id`, если поле не пустое.

### 6.4. Заявки на вывод средств

Модель `WithdrawalRequest` отвечает за ручной вывод средств. Поддерживаются способы:

- СБП;
- банковская карта.

Статусы заявки:

- ожидает обработки;
- в обработке;
- выплачено;
- отклонено.

При создании заявки сумма резервируется: с баланса пользователя списывается сумма и создается транзакция списания. Если администратор отклоняет заявку, сумма возвращается пользователю на баланс отдельной транзакцией.

### 6.5. Коллекции и предметы

Модель `Collection` хранит коллекции пользователя:

- название;
- описание;
- цвет;
- флаг публичности;
- владелец.

Модель `Item` хранит предмет:

- название;
- описание;
- цена;
- флаг продажи;
- владелец;
- коллекция;
- основное изображение.

Модель `ItemImage` добавляет галерею фотографий для предмета. Это позволяет загружать несколько изображений, просматривать их в карточках и листать в интерфейсе.

### 6.6. Вишлист

`WishlistItem` связывает пользователя и предмет. Пользователь может добавить интересующий предмет в избранное. На основе вишлиста также можно уведомлять о важных изменениях, например о смене цены.

### 6.7. Чаты и сообщения

`Chat` хранит переписку между покупателем и продавцом. В чате также хранится состояние сделки:

- ожидание согласия;
- продавец согласен;
- оплачено;
- отправлено;
- прибыло;
- завершено.

`Message` хранит сообщения, отправителя, дату и флаг прочтения.

Чат не удаляется физически после завершения сделки. Он становится архивным. Покупатель и продавец могут скрыть архивный чат локально только для себя.

### 6.8. Сделки

Для каждой сделки создается отдельная модель `Deal` с UUID. Она связана с чатом и хранит:

- покупателя;
- продавца;
- предмет;
- базовую цену продавца;
- цену покупателя с сервисным сбором;
- сумму сервисного сбора;
- статус сделки;
- статус эскроу;
- удержанную сумму;
- даты оплаты, возврата, зачисления продавцу;
- администратора, который провел ручную операцию;
- административную заметку.

Это нужно для прозрачного учета сделок в Django Admin и для возможности быстро найти сделку по идентификатору.

### 6.9. Новости

`Article` хранит новость:

- заголовок;
- текст;
- дату публикации;
- источник;
- внешний ID источника;
- изображение обложки.

`ArticleImage` хранит дополнительные изображения новости. Новости могут содержать несколько картинок и отображаются с галереей.

### 6.10. Поддержка

`SupportTicket` хранит обращение пользователя:

- тему;
- статус;
- пользователя;
- дату создания и обновления.

`SupportMessage` хранит сообщения внутри тикета. Администратор может отвечать пользователю. При новых тикетах и сообщениях могут отправляться Telegram-уведомления.

## 7. Основные пользовательские сценарии

### 7.1. Регистрация и вход

1. Пользователь заполняет username, email и пароль.
2. Backend создает `PendingRegistration`, сохраняет хэш пароля и отправляет письмо.
3. Пользователь переходит по ссылке подтверждения.
4. Backend создает полноценный аккаунт.
5. Пользователь входит через форму.
6. Backend выдает JWT в httpOnly cookie.
7. Frontend получает профиль через `/api/accounts/me/` и открывает личный кабинет.

Пароль не хэшируется на frontend перед отправкой. Это нормально для веб-приложений: пароль передается по HTTPS, а хэширование выполняется на сервере надежным механизмом Django. Хранить хэширование на клиенте не требуется и часто ухудшает безопасность.

### 7.2. Игровой онбординг

После входа пользователь видит обучающий квест. Он состоит из шагов:

1. заполнить телефон;
2. выбрать пункт выдачи СДЭК;
3. создать первую коллекцию;
4. добавить первый предмет.

За шаги начисляется XP и показывается прогресс. Если шаг уже был выполнен, он сохраняется в `onboarding_completed_steps` и не откатывается назад. Например, если пользователь позже удалит телефон или коллекцию, пройденный шаг не появится снова как незавершенный.

Зачем это разработано:

- уменьшить порог входа для нового пользователя;
- объяснить, какие данные нужны для сделок;
- привести пользователя к первой полезной активности;
- сделать onboarding более наглядным и игровым.

### 7.3. Работа с коллекциями и предметами

Пользователь может:

- создавать коллекции;
- задавать название, описание, цвет и публичность;
- добавлять предметы;
- загружать несколько фотографий;
- редактировать фотографии;
- удалять фотографии;
- назначать цену;
- включать продажу предмета.

Для покупателей цена показывается с сервисным сбором. Для продавца цена остается такой, какую он указал.

### 7.4. Поиск

Поиск предметов поддерживает:

- текстовый запрос;
- минимальную цену;
- максимальную цену;
- фильтр наличия фотографии;
- сортировку по дате или цене.

Это упрощает сценарий поиска нужного коллекционного предмета и делает сервис похожим на полноценную витрину.

### 7.5. Вишлист

Пользователь может добавить предмет в избранное. Это нужно для быстрого возвращения к интересующим предметам и будущих уведомлений о важных изменениях.

### 7.6. Чат

Чат нужен для переговоров между покупателем и продавцом. Он работает через WebSocket с HTTP-fallback. Это значит:

- новые сообщения могут приходить в реальном времени;
- если WebSocket недоступен, базовая работа остается через HTTP;
- счетчики непрочитанных сообщений обновляются через realtime-события.

В чате отображается код вида `CHAT-123`. Пользователь может назвать этот код администратору, а администратор может найти чат или сделку в Django Admin.

### 7.7. Эскроу-сделка

Жизненный цикл сделки:

1. Покупатель открывает чат по предмету.
2. Продавец соглашается продать.
3. Покупатель оплачивает цену с учетом сервисного сбора 7%.
4. Деньги списываются с баланса покупателя и удерживаются в сделке.
5. Продавец передает товар в СДЭК.
6. Создается заказ СДЭК.
7. После доставки покупатель подтверждает получение.
8. Базовая цена предмета зачисляется продавцу.
9. Предмет удаляется из коллекции продавца.
10. Сделка переходит в архив.

Средства не переводятся продавцу сразу после оплаты. Они удерживаются до подтверждения получения. Это снижает риск мошенничества и делает сделку безопаснее.

Если возникает спор, администратор может:

- вручную вернуть удержанные деньги покупателю;
- вручную зачислить удержанные деньги продавцу.

### 7.8. Сервисный сбор

Платформа добавляет к цене для покупателя сервисный сбор 7%. Продавец видит и получает свою базовую цену. Покупатель видит итоговую цену.

Пример:

- продавец указал 1000 рублей;
- сервисный сбор 7% = 70 рублей;
- покупатель оплачивает 1070 рублей;
- продавцу после завершения сделки зачисляется 1000 рублей;
- 70 рублей остаются как комиссия платформы.

Такой подход позволяет монетизировать платформу без уменьшения суммы, которую продавец сам назначил.

### 7.9. Вывод средств

После успешных сделок продавец может вывести деньги с баланса. В MVP реализован ручной вывод:

- через СБП;
- на банковскую карту.

Пользователь создает заявку, вводит сумму и реквизиты. Система проверяет сумму, резервирует деньги и создает заявку. Администратор обрабатывает заявку в Django Admin.

Почему выбран ручной вывод:

- для MVP не требуется сложная интеграция с выплатным провайдером;
- проще контролировать спорные ситуации;
- можно быстрее запустить платформу и проверить бизнес-сценарий.

Для production в будущем вывод на карту лучше заменить токенизированными выплатами через платежного провайдера.

### 7.10. Поддержка

Пользователь может создать тикет поддержки по теме:

- платежи;
- доставка;
- сделка;
- аккаунт;
- другое.

Администратор видит тикеты, отвечает пользователю и меняет статус. Пользователь может подтвердить, что вопрос решен.

### 7.11. Новости

На платформе есть новостной раздел. Он поддерживает:

- ручное создание новостей редактором;
- несколько изображений в новости;
- lightbox/просмотр картинок;
- безопасное жирное выделение текста через Markdown-синтаксис `**текст**`;
- AI-импорт новостей с внешнего сайта.

## 8. Подключенные интеграции

### 8.1. ЮKassa

ЮKassa используется для платежных сценариев:

- создание платежа;
- проверка платежа;
- обработка webhook;
- анализ причины отмены платежа;
- защита от двойного зачисления.

Используются переменные окружения:

- `YOOKASSA_SHOP_ID`;
- `YOOKASSA_SECRET_KEY`.

Реальные значения не должны храниться в Git.

Защита ЮKassa:

- проверка metadata `user_id`;
- проверка `payment_id`;
- partial unique constraint на `payment_yookassa_id`;
- IP whitelist для webhook;
- логирование `cancellation_details`;
- возврат понятных причин отмены на frontend.

### 8.2. СДЭК

СДЭК используется для выбора пункта выдачи и создания заказа доставки.

Реализовано:

- запрос пунктов выдачи;
- отображение карты выбора ПВЗ;
- сохранение выбранного пункта в профиле;
- требование телефона и ПВЗ перед сделкой;
- нормализация телефона к формату `+7...`;
- создание заказа при отправке товара;
- fallback на демо-точки, если API недоступен или не настроен.

Переменные окружения:

- `CDEK_BASE_URL`;
- `CDEK_CLIENT_ID`;
- `CDEK_CLIENT_SECRET`.

### 8.3. Google Gemini

Gemini используется для автоматической генерации обзорных новостей.

Сценарий:

1. Celery Beat запускает задачу по расписанию.
2. Backend парсит новости с `https://www.numizmatik.ru/news`.
3. Несколько найденных новостей объединяются в один набор источников.
4. Тексты отправляются в Gemini.
5. Gemini переписывает материал своими словами и формирует большую обзорную статью.
6. Изображения скачиваются с сайта-источника и прикрепляются к статье.
7. Новость публикуется в разделе `/news`.

Реализованы:

- dry-run режим без публикации;
- защита от дублей по агрегированному external_id;
- fallback на запасную модель;
- emergency-режим без AI для отладки;
- безопасное отображение жирного текста.

Переменные окружения:

- `GEMINI_API_KEY`;
- `GEMINI_MODEL`;
- `GEMINI_FALLBACK_MODEL`;
- `NEWS_IMPORT_ENABLED`;
- `NEWS_IMPORT_INTERVAL_MINUTES`;
- `NEWS_IMPORT_LIMIT`;
- `NEWS_IMPORT_MAX_IMAGES`.

### 8.4. Telegram Bot API

Telegram-бот используется для уведомления администратора о поддержке.

События:

- создан новый тикет;
- пользователь написал новое сообщение в тикете.

Переменные окружения:

- `TELEGRAM_NOTIFICATIONS_ENABLED`;

Также реализована management-команда для получения chat id после команды `/start`.

Email используется для:

### 8.6. Sentry

Sentry подключается опционально для мониторинга ошибок backend и frontend.

Переменные:

## 9. Безопасность

В проекте реализован отдельный комплекс мер безопасности.

### 9.1. Авторизация

Используется JWT, но токены не хранятся в `localStorage`. Access и refresh выдаются в httpOnly cookie. Это уменьшает риск кражи токена через XSS.

Дополнительно:

- refresh-токены ротируются;
- старые refresh-токены попадают в blacklist;
- legacy JSON JWT endpoints выключены по умолчанию;
- Bearer-auth выключен по умолчанию;
- WebSocket access-token через query string выключен по умолчанию;
- WebSocket авторизуется через cookie.

### 9.2. CSRF и CORS

Для небезопасных методов frontend добавляет `X-CSRFToken`. На backend включены:

- CSRF middleware;
- SameSite cookie;
- CORS allow credentials;
- список разрешенных origin;
- Origin protection для небезопасных API-запросов.

### 9.3. Ограничение частоты запросов

Добавлены throttle-лимиты:

- login;
- register;
- payment;
- support;
- chat messages.

Это защищает от brute-force и спама.

### 9.4. Защита от SQL-инъекций

Проект использует Django ORM и DRF. SQL-запросы строятся через ORM, а пользовательские данные не вставляются вручную в SQL-строки. Это снижает риск SQL-инъекций.

### 9.5. Защита от XSS

React по умолчанию экранирует текст. В новостях поддерживается ограниченный Markdown-синтаксис для жирного текста, но произвольный HTML не исполняется. Токены находятся в httpOnly cookie и недоступны JavaScript-коду.

### 9.6. Загрузка файлов

Добавлена централизованная валидация изображений:

- ограничение размера файла;
- ограничение количества изображений;
- whitelist content-type;
- проверка изображений до сохранения.

Валидация применяется к:

- аватарам;
- фотографиям предметов;
- галереям предметов;
- изображениям новостей.

### 9.7. Защита платежей

Реализовано:

- проверка владельца платежа по metadata;
- идемпотентность webhook;
- уникальность `payment_yookassa_id`;
- IP whitelist для webhook;
- блокировки и `select_for_update` при операциях с балансом;
- использование `F()`-выражений при изменении баланса.

### 9.8. Security headers

В nginx/Caddy и Django-настройках используются:

- CSP;
- `X-Content-Type-Options`;
- `X-Frame-Options`;
- `Referrer-Policy`;
- `Permissions-Policy`;
- `Cross-Origin-Opener-Policy`.

## 11. Production-деплой

Проект подготовлен к запуску через Docker Compose.

Контейнеры:

- `postgres` - база данных PostgreSQL;
- `redis` - Redis для Channels и Celery;
- `backend` - Django ASGI через Daphne;
- `celery` - worker фоновых задач;
- `celery-beat` - расписание задач, включая AI-импорт новостей;
- `frontend` - nginx со сборкой React;
- `caddy` - HTTPS reverse proxy для production.

В production используется команда:

```bash
docker compose --env-file .env.docker -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Фронтенд собирается с `REACT_APP_API_URL=/api`, поэтому браузер ходит на тот же домен. Это важно для cookie-авторизации и WebSocket.

Media и static отдаются через nginx на том же origin:

- `/media/...`;
- `/static/...`.

Сайт был развернут на VPS. Домены указывают на IP сервера через DNS A-записи. HTTPS выпускается Caddy автоматически.

## 16. Краткий вариант описания для введения

CollectIT представляет собой веб-платформу для коллекционеров, объединяющую функции личного каталога, витрины предметов, маркетплейса, безопасной сделки, доставки, уведомлений, новостей и поддержки. Система разработана на основе клиент-серверной архитектуры: backend реализован на Django REST Framework, frontend - на React, база данных - PostgreSQL, realtime-взаимодействие - через WebSocket и Redis, фоновые задачи - через Celery. Для production-запуска используется Docker Compose и Caddy с автоматическим HTTPS.

Ключевой особенностью платформы является безопасная сделка с удержанием средств. Покупатель оплачивает предмет с учетом сервисного сбора, деньги удерживаются в системе, продавец передает товар в доставку, а средства переводятся продавцу только после подтверждения получения покупателем. Такой подход повышает доверие между участниками сделки и снижает риск мошенничества.

Дополнительно реализованы интеграции с ЮKassa, СДЭК, Google Gemini, Telegram Bot API, SMTP и Sentry. Система включает игровой онбординг, галерею фотографий предметов, поиск с фильтрами, поддержку, новости, ручной вывод средств и административные инструменты для контроля сделок и обращений.

## 18. Дополнение от 8 июня 2026: согласия при регистрации

В регистрацию добавлена юридически значимая фиксация согласий пользователя:

- на странице регистрации отображаются два обязательных чекбокса:
  - принятие пользовательского соглашения и правил сервиса;
  - согласие на обработку персональных данных;
- текст рядом с каждым чекбоксом открывает модальное окно с текстом соответствующего документа;
- frontend блокирует отправку формы без обеих галочек;
- backend API также требует `terms_accepted=true` и `personal_data_accepted=true`, поэтому обход интерфейса прямым HTTP-запросом не позволяет зарегистрироваться без согласий;
- факт принятия сохраняется сначала в `PendingRegistration`, потому что аккаунт создается только после подтверждения email;
- после подтверждения email дата, версия документа, IP и user-agent переносятся в модель `User`;
- сведения о согласиях доступны администратору в Django Admin.

Это изменение связано с обработкой персональных данных, платежными и сделочными сценариями платформы: без согласия пользователь не должен переходить к функциям сервиса, где используются email, телефон, ПВЗ, чаты, платежи, доставка и поддержка.
